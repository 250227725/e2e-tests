# Фреймворк разработки E2E-тестов

Самостоятельный фреймворк для организации разработки E2E UI-тестов на Playwright Test и TypeScript в OpenCode. Задаёт единый подход к описанию Test Case (TC) и Action, исследованию интерфейса, хранению селекторов, ролям с подготовленными сессиями, реализации тестов и диагностике результатов. Разработкой каждого теста занимается агент — от исследования интерфейса до готового кода — по утверждённым спецификациям, без импровизации там, где спецификация неоднозначна.

Фреймворк не привязан к конкретному проекту: перед началом работы он инициализируется под фактическую архитектуру, окружение и бизнес-специфику тестируемой системы (см. «Установка и настройка» ниже).

## Ключевые концепции

Прежде чем пользоваться командами, полезно понимать пять базовых понятий — остальное фреймворка выстроено вокруг них.

**Test Case (TC)** — одно проверяемое бизнес-условие. Источник истины для того, что и зачем проверяется. Хранится в `docs/test-cases/`, идентификатор — `TC-<ДОМЕН>_<slug>` (домен — область фреймворка вроде `AUTH`/`CG`, slug — короткий английский перифраз проверяемого условия, например `login-succeeds-without-extended-profile`).

**Action** — переиспользуемое действие с чётким контрактом (входные параметры, шаги, варианты успешного результата, выходные данные). Идентификатор — `AA-<CODE>`, документ в `docs/actions/`, программная реализация — в `actions/AA-<CODE>.ts`. Action — не только UI-действие: получение данных из внешнего источника или генератор случайных данных тоже оформляются как Action, а не как код внутри теста напрямую (см. `test-data-and-environment.md`).

**Роль** — заранее подготовленная, сохранённая сессия (например, «Администратор», «Пользователь»), которую TC может использовать вместо собственной аутентификации. Реестр ролей — `docs/roles.md`, настраивается командой `/configure-roles`. TC ссылается на роль в разделе `## Роль`; при отсутствии роли TC выполняет аутентификацию сам, как обычный Action.

**JSON-спецификация селекторов** — `<ID>.selectors.json` рядом с каждым TC/Action. В отличие от самого TC/Action, это не утверждённая документация, а регенерируемый артефакт реализации: создаётся и обновляется на `/implement-tc`, свободно перезаписывается при дрейфе локатора (изменился id/атрибут элемента), без согласования с пользователем.

**Хэш и edit-режим.** Каждая программная реализация хранит в первой строке хэш источника (раздела документа, из которого она получена). `/edit-aa` и `/edit-tc` при изменении документа сверяют хэш и по необходимости каскадно удаляют устаревшую реализацию — свою и, при смене контракта Action, зависимых TC. Подробности — `playwright-implementation.md`.

## Установка и настройка

Выполните один раз при первом подключении фреймворка к проекту — до создания первого TC.

### 1. Технические требования

- [OpenCode](https://opencode.ai).
- Python 3.10 или новее (используется только стандартная библиотека — ничего дополнительно устанавливать не нужно).
- Node.js и npm — для Playwright Test и MCP-сервиса в целевом проекте.
- [Playwright Test](https://playwright.dev) установлен в целевом проекте (`npm install --save-dev @playwright/test`, затем `npx playwright install`).

### 2. MCP-сервис браузерной автоматизации (обязательно)

Фреймворк не привязан к конкретному MCP-серверу — важен только результат (валидные Playwright-локаторы), не то, каким инструментом агент осматривал страницу. Подходит официальный [`@playwright/mcp`](https://www.npmjs.com/package/@playwright/mcp) от Microsoft, ChromeDevTools MCP или другой сервис браузерной автоматизации.

Добавьте сервис в `opencode.json` в корне проекта. Точный синтаксис может отличаться между версиями OpenCode — сверьтесь с официальной документацией: <https://opencode.ai/docs/mcp-servers/>. Ориентировочный вид записи (уточните актуальный формат по ссылке выше перед использованием):

```json
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "playwright": {
      "type": "local",
      "command": ["npx", "-y", "@playwright/mcp@latest"]
    }
  }
}
```

Без подключённого MCP-сервиса `/research-tc`, `/implement-tc` и `/explore` не смогут исследовать интерфейс.

### 3. Переменные окружения

Создайте `.env.dev` (или аналогичный файл конфигурации, принятый в целевом проекте) с базовым URL и данными учётной записи окружения. Конкретные имена переменных — на усмотрение проекта, фреймворк их не угадывает (см. п. 4).

### 4. Контекст проекта — `/init-project`

Запустите `/init-project` в OpenCode. Команда в диалоге (по одному вопросу за раз) соберёт особенности конкретного проекта и запишет их в раздел «Контекст проекта» файла `AGENTS.md`:

1. SPA-приложение или переходы вызывают полную перезагрузку страницы.
2. Доступен ли API для подготовки тестовых данных, или строго через UI.
3. Есть ли бизнес-сущности, которые нельзя создать через UI и нужно использовать как готовые.
4. Имена переменных окружения для базового URL и учётных данных.
5. Расположение документации, если отличается от `docs/actions/`/`docs/test-cases/` по умолчанию.
6. Использовать существующий в проекте линтер/форматтер/генератор данных, или подключить рекомендуемые ESLint, Prettier и Faker.

Без выполненного `/init-project` агент не будет знать проектных допущений и будет останавливаться вопросами по ходу работы, которые можно было закрыть один раз заранее. При изменении этих особенностей в будущем запустите `/init-project` повторно — он покажет текущий раздел и спросит только про то, что изменилось.

### 5. ESLint, Prettier, Faker — по решению из `/init-project` (не обязательно)

Если на шаге 4 выше вы выбрали подключить рекомендуемые инструменты, а не использовать уже существующие в проекте:

```bash
npm install --save-dev eslint prettier
npx eslint --init
npm install --save-dev @faker-js/faker
```

Faker (или аналог) используется **только внутри реализации Action-генераторов данных** (`actions/AA-<CODE>.ts`), никогда не вызывается из кода теста напрямую — см. `test-data-and-environment.md`.

## Типичный цикл работы

1. `/init-project` — один раз, при подключении к новому проекту (см. выше).
2. `/explore <описание раздела и задачи>` — по желанию, если нужно предварительно исследовать интерфейс и подготовить черновик кандидатов Action/TC (`docs/exploration/`) до формального создания документации.
3. `/create-aa` / `/create-tc` — интерактивно создать AA/TC документ по утверждённому шаблону.
4. `/configure-roles` — по желанию, если сценарии проекта выигрывают от переиспользуемых подготовленных сессий (например, «Администратор»).
5. `/research-tc <TC-ID>` — исследовать TC через MCP без изменения кода, если нужно проверить выполнимость до полной реализации.
6. `/implement-tc <TC-ID>` — полный цикл: исследование, реализация недостающих Action, спецификация селекторов, сам тест, проверки.
7. `/run-tc <TC-ID>` — изолированный повторный запуск уже реализованного TC.
8. `/edit-aa <AA-ID>` / `/edit-tc <TC-ID>` — изменить утверждённый документ; реализация пересоздаётся автоматически по хэшу.
9. `/update-index` — по желанию, обновить сводный `docs/index.md` по фактическому составу документации.

Полный прогон всего набора тестов выполняется штатными средствами Playwright Test (`npx playwright test`), не отдельной командой фреймворка.

## Справочник команд

| Команда | Назначение |
|---|---|
| `/init-project` | Собрать или обновить раздел «Контекст проекта» в `AGENTS.md`. |
| `/explore <описание>` | Исследовать раздел системы через MCP, подготовить черновой материал для будущих Action/TC (`docs/exploration/`). |
| `/create-aa [описание]` | Интерактивно создать новый Action. |
| `/create-tc [описание]` | Интерактивно создать новый TC. |
| `/edit-aa <AA-ID>` | Изменить существующий Action; при смене контракта каскадно пересоздаёт зависимые реализации. |
| `/edit-tc <TC-ID>` | Изменить существующий TC; пересоздаёт его реализацию. |
| `/configure-roles` | Добавить, изменить или удалить роль и её подготовленную сессию. |
| `/research-tc <TC-ID>` | Исследовать TC через MCP без изменения кода. |
| `/implement-tc <TC-ID>` | Полный цикл: исследование, реализация, проверка одного TC. |
| `/run-tc <TC-ID>` | Изолированно запустить один уже реализованный TC. |
| `/update-index` | Пересобрать `docs/index.md` по фактическому составу TC и Action. |

## Структура репозитория

Полный и всегда актуальный список файлов и их владельцев — в [`STRUCTURE.md`](./STRUCTURE.md). Кратко:

```
AGENTS.md               — постоянные правила фреймворка + «Контекст проекта»
STRUCTURE.md             — состав комплекта, владельцы правил
docs/
  actions/               — утверждённые спецификации Action (+ *.selectors.json)
  test-cases/            — утверждённые спецификации TC (+ *.selectors.json)
  roles.md               — реестр ролей
  index.md                — авто-индекс TC/Action (/update-index)
  planned-changes.md      — запланированные, ещё не созданные сценарии
  exploration/            — черновики после /explore
actions/                 — программная реализация Action (AA-<CODE>.ts)
fixtures/roles.ts         — резолвер сохранённых состояний по коду роли
tmp/plans/                — планы выполнения задач (не коммитятся)
.opencode/
  command/                — команды из справочника выше
  instructions/           — правила, на которые ссылается AGENTS.md
  templates/               — шаблоны документов и отчётов
  scripts/document_authoring.py — проверка, создание, агрегация TC/Action
```

## Диагностика и статусы

Классификация ошибок, формат отчётов и статусы (`DONE`/`BLOCKED`/`FAILED`, `PASSED`/`FAILED`/`NOT_RUN`) описаны в `diagnostics.md`. Если агент возвращает `BLOCKED` — это означает, что документация и наблюдаемое поведение системы разошлись и нужно решение человека; сам агент трактовку не выбирает (см. `AGENTS.md`, «Источники истины»).

## Дальнейшее чтение

- [`AGENTS.md`](./AGENTS.md) — постоянные ограничения, источники истины, планирование задачи, полный список владельцев правил.
- [`STRUCTURE.md`](./STRUCTURE.md) — исчерпывающий состав комплекта.
- `.opencode/instructions/` — по одной инструкции на тему: создание документации, реализация TC, данные и окружение, Playwright-код, локаторы и селекторы, роли, исследование, диагностика.
