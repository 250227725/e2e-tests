# AGENTS.md

## Назначение

Репозиторий предназначен для разработки независимых E2E UI-тестов веб-приложения на Playwright Test и TypeScript.

Работа ведётся по утверждённым спецификациям Test Case (TC) и Atomic Action (AA). Агент реализует требования, исследует фактический интерфейс через подключённый MCP-сервис браузерной автоматизации, выбирает устойчивые локаторы, выявляет неоднозначности до реализации и сохраняет стабильность существующих тестов.

## Постоянные ограничения

- Взаимодействие с системой выполняется только через веб-интерфейс.
- Для TC может быть определена конкретная учётная запись; иначе используется базовая учётная запись окружения.
- Все остальные необходимые бизнес-сущности создаются текущим тестом через UI, если TC явно не указывает использовать существующую сущность.
- Существующие бизнес-сущности не используются как предусловия, если это прямо не указано в TC.
- Тесты не зависят от порядка выполнения, общего состояния и данных других тестов.
- Очистка созданных данных не требуется, если обратное не указано в TC.
- Тесты выполняются локально.
- Архитектура не должна препятствовать будущему параллельному выполнению.

## Контекст проекта

Раздел формируется командой `/init-project` и содержит факты конкретного проекта (особенности архитектуры приложения, доступность API для подготовки данных, готовые сущности, именование переменных окружения, расположение документации, используемый инструментарий), а не постоянные правила фреймворка. Не редактируется вручную вне этого процесса — при необходимости изменить содержимое выполните `/init-project` повторно.

*Не заполнено. Выполните `/init-project`.*

## Источники истины

- Проверяемое бизнес-условие определяется TC.
- Контракт атомарного действия определяется AA.
- Связь `TC → AA` определяется разделом `Зависимости` соответствующего TC.
- Фактическое устройство интерфейса определяется исследованием через подключённый MCP-сервис браузерной автоматизации.
- Спецификация селекторов фиксирует результат предыдущего исследования, но не заменяет проверку реального интерфейса.
- TypeScript-код описывает текущую реализацию, но не изменяет смысл TC или AA.

При противоречии между TC и AA агент возвращает `BLOCKED` и не выбирает трактовку самостоятельно. Фактическое поведение приложения не отменяет утверждённое требование.

## Проектная документация

Все существующие TC, AA и selector-спецификации считаются утверждёнными. Selector-спецификации хранятся рядом с документом как `<DOCUMENT-ID>.selectors.json`.

Агент не изменяет, не перезаписывает, не перемещает и не удаляет утверждённую документацию, кроме как в рамках команд `/edit-aa` и `/edit-tc`, описанных ниже.

Исключение: раздел «Контекст проекта» в этом файле не является утверждённой документацией TC/AA и обновляется командой `/init-project` в штатном режиме.

Создание новой спецификации разрешено только командами:

- `/create-aa`;
- `/create-tc`.

Изменение существующей утверждённой спецификации разрешено только командами `/edit-aa` и `/edit-tc`. Оба процесса ведут диалог по правилам `documentation-authoring.md`; условия пересоздания зависимой программной реализации при изменении AA или TC описаны в `playwright-implementation.md`.

Новый или изменённый документ сохраняется только после согласования полного текста с пользователем. После сохранения он считается утверждённым.

Если существующая документация требует изменения вне явного вызова `/edit-aa`/`/edit-tc` (например, обнаружено в ходе `/research-tc` или `/implement-tc`), агент:

1. останавливает выполнение в точке, после которой изменение обязательно;
2. возвращает `BLOCKED`;
3. описывает проблему;
4. предлагает готовую редакцию или точный diff;
5. указывает затронутые документы и разделы.

Обсуждение в диалоге не заменяет утверждённую документацию.

## Окружение и секреты

- Стартовый URL и данные учётных записей берутся из существующей конфигурации окружения.
- Имена переменных определяются по фактическому проекту (см. «Контекст проекта») и не угадываются.
- Секреты не выводятся в ответы, логи и отчёты и не копируются в код.
- файлы `.env.*` не добавляются в коммиты.
- директория `tmp/` (включая `tmp/plans/`) не добавляется в коммиты.
- Значения учётных записей не изменяются без явной команды.
- Отсутствие обязательной переменной приводит к понятной ошибке.

## Безопасность изменений

Перед изменением файлов проверь текущее состояние репозитория.

Запрещено:

- перезаписывать несвязанные изменения пользователя;
- откатывать или удалять файлы вне текущей задачи;
- выполнять destructive-команды Git;
- создавать commit, выполнять push или изменять историю без явной команды;
- форматировать весь проект, если задача затрагивает отдельные файлы;
- изменять код тестируемого приложения;
- маскировать дефект приложения изменением ожиданий;
- отключать или ослаблять проверки и существующие тесты;
- добавлять retries или увеличивать timeout без диагностики;
- заявлять о проверке, которая фактически не запускалась;
- выдавать результат предыдущей сессии за результат текущего запуска.

Изменения ограничиваются минимальным набором необходимых файлов.

## Планирование и восстановление задачи

Перед началом выполнения любой задачи агент анализирует запрос и артефакты проекта, формирует план из отдельных шагов и сохраняет его в `tmp/plans/<команда>_<идентификатор-цели>_<timestamp>.md`. План кратко показывается пользователю в начале выполнения, без запроса подтверждения.

По ходу работы агент отмечает выполненные шаги в файле плана.

Если сессия прерывается, следующий запуск читает существующий план и продолжает с первого невыполненного шага, перепроверяя фактическое состояние проекта — не доверяя слепо отметке «выполнено».

После завершения задачи (`DONE`, `BLOCKED` или `FAILED`) файл плана перемещается в `tmp/plans/archive/`, не удаляется.

## Статусы

Не смешивай три разных типа значений.

**Статус работы агента:**

- `DONE` — порученная работа завершена;
- `BLOCKED` — требуется решение пользователя или изменение документации;
- `FAILED` — работа не завершена по технической причине.

**Результат теста:** `PASSED | FAILED | NOT_RUN`.

Работа может завершиться `DONE` при результате теста `FAILED`, если корректный тест выявил дефект приложения.

Полный прогон набора тестов выполняется штатными средствами Playwright Test, не отдельной командой фреймворка.

## Команды OpenCode

### Инициализация проекта

- `/init-project` — интерактивно собрать или обновить раздел «Контекст проекта».

### Создание документации

- `/create-aa [описание]` — интерактивно создать и согласовать новый AA.
- `/create-tc [описание]` — интерактивно создать и согласовать новый TC.

### Редактирование документации

- `/edit-aa <AA-ID>` — интерактивно изменить существующий AA; при изменении сигнатуры или логики пересоздаёт зависимую программную реализацию (свою и, при изменении сигнатуры, зависимых TC).
- `/edit-tc <TC-ID>` — интерактивно изменить существующий TC; пересоздаёт его реализацию.

### Работа с одним TC

- `/research-tc <TC-ID>` — исследовать TC через MCP без изменения кода.
- `/implement-tc <TC-ID>` — исследовать, реализовать и проверить один TC.
- `/run-tc <TC-ID>` — изолированно запустить один реализованный TC.

### Индекс

- `/update-index` — пересобрать `docs/index.md` по фактическому составу TC и AA.

## Подключение контекста

Не загружай все правила и документы заранее.

Команды сами подключают необходимые файлы из `.opencode/instructions/` и `.opencode/templates/`. При работе без команды прочитай только инструкцию, относящуюся к текущей задаче:

- создание документации — `documentation-authoring.md`;
- инициализация или обновление контекста проекта — `project-initialization.md`;
- реализация TC — `test-development.md`;
- данные и окружение — `test-data-and-environment.md`;
- Playwright-код — `playwright-implementation.md`;
- интерфейс и локаторы — `selector-research.md`;
- диагностика — `diagnostics.md`;

Для одного TC открывай только целевой TC, AA из его раздела `Зависимости`, связанные спецификации селекторов и непосредственно затронутый код.

## Владельцы правил

- постоянные ограничения, контекст проекта, планирование и восстановление задачи — `AGENTS.md`;
- создание и редактирование TC и AA — `documentation-authoring.md`;
- инициализация и контекст проекта — `project-initialization.md`;
- процесс реализации TC — `test-development.md`;
- данные и контекст теста — `test-data-and-environment.md`;
- Playwright-код, реализация AA, хэши, edit-режим — `playwright-implementation.md`;
- локаторы, селекторы и их JSON-спецификация — `selector-research.md`;
- ошибки, статусы и отчёты — `diagnostics.md`;
- создание, проверка и агрегация TC/AA — `.opencode/scripts/document_authoring.py`;
- форма документа или отчёта — соответствующий файл в `.opencode/templates/`.

Команды определяют только точку входа, подключаемые материалы, границы операции и ожидаемый результат. Они не должны дублировать тематические правила.
