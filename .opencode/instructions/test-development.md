# Реализация одного Test Case

## Область применения

Инструкция определяет процесс исследования и реализации одного утверждённого TC.

Работай только с TC, указанным в команде. Не анализируй другие сценарии без необходимости поиска затронутого общего кода.

## 1. Загрузка контекста

Прочитай:

1. целевой `TC-*.md`;
2. только Action из его раздела `Зависимости`;
3. JSON-спецификации селекторов целевого TC и используемых Action, если они существуют (на этапе `/research-tc` их в норме ещё нет — это не исключение, а обычный случай);
4. существующий целевой тест, реализации использованных Action (`actions/AA-<CODE>.ts`) и непосредственно связанный общий код, если они существуют.

Не загружай остальные TC, Action и селекторы заранее.

## 2. Статическая проверка

До работы с интерфейсом проверь:

- существуют ли все указанные Action;
- не противоречат ли TC и Action;
- определено ли одно проверяемое бизнес-условие;
- определены ли обязательные тестовые данные;
- можно ли получить и создать необходимые данные через UI (с учётом явных исключений, указанных в TC для готовых сущностей);
- можно ли однозначно подтвердить один из вариантов успешного результата каждого подготовительного Action;
- совместимы ли последовательные Action;
- не требует ли сценарий существующей бизнес-сущности или результата другого теста, если это прямо не указано в TC;
- если TC указывает роль (раздел «Роль») — существует ли эта роль в `docs/roles.md`. Скрипт (`document_authoring.py validate --kind tc`) уже проверяет это при сохранении документа, но при работе с ранее сохранённым TC проверь актуальность отдельно: роль могла быть удалена из `docs/roles.md` после создания TC. Если роль не найдена — верни `BLOCKED`, укажи выполнить `/configure-roles`.

При блокирующей неоднозначности действуй по корневому `AGENTS.md` и шаблону `blocked-report.md`.

## 3. Dry-run

До запуска MCP сформируй внутренний пошаговый план:

- выбор учётной записи (для TC с указанной ролью — загрузка подготовленного состояния, не аутентификация заново);
- подготовка и генерация данных;
- последовательность Action;
- переходы между страницами;
- значения, передаваемые через контекст теста;
- основная проверка TC.

Отдельное подтверждение dry-run не требуется, если документация однозначна.

## 4. Исследование и проверка выполнимости

Действуй по `selector-research.md`.

До написания тестового кода выполни сценарий через подключённый MCP-сервис браузерной автоматизации и проверь:

- выполнимость каждого подготовительного действия;
- передачу данных между шагами;
- достижимость основной проверки;
- достижение одного из вариантов успешного результата каждого Action;
- соответствие наблюдаемого результата основной проверке TC.

На этапе `/research-tc` результат исследования фиксируется только в отчёте (`completion-report.md`/`blocked-report.md`) — JSON-спецификация селекторов не создаётся, файлов не остаётся.

Если TC указывает роль (раздел «Роль»): MCP-исследование не умеет загружать сохранённое состояние сессии (`storageState`) — это механизм Playwright Test, отдельный от MCP-сессии агента. Пройди подготовку роли вживую через MCP (те же шаги, что описаны для роли в `docs/roles.md`), чтобы достичь нужного для исследования TC состояния интерфейса. Это не противоречит тому, что в реализации (`/implement-tc`) TC будет использовать уже готовое состояние без повторной аутентификации — исследование и реализация используют разные механизмы для достижения одного и того же состояния.

При необходимости изменения утверждённой документации верни `BLOCKED`. Документы вне `/edit-aa`/`/edit-tc` не изменяй.

## Использование Action

При выполнении Action достаточно подтвердить один из вариантов, перечисленных в разделе `Варианты успешного результата`. Все перечисленные варианты считаются успешными.

Если ни один вариант не достигнут:

1. считать Action выполненным неуспешно;
2. немедленно остановить выполнение текущего TC;
3. не продолжать основную проверку и последующие действия;
4. классифицировать причину по `diagnostics.md`.

Не добавляй в реализацию ветвление по отрицательным исходам, если оно не требуется отдельным TC. Не превращай неописанный исход в новый результат Action.

Если дальнейшим шагам нужен конкретный успешный вариант, используй только выходные данные, явно определённые в Action.

## 5. Реализация

Реализация выполняется только в рамках `/implement-tc` (не `/research-tc`).

1. Для каждой Action из «Зависимости», у которой отсутствует `actions/AA-<CODE>.ts`, реализуй её первой — по правилам `playwright-implementation.md`. Если файл уже существует, проверь хэши источника (раздел «Проверка актуальности реализации» ниже) перед использованием.
2. Создай или обнови JSON-спецификацию селекторов для TC и всех задействованных Action по результатам исследования — используй `document_authoring.py write-selectors`, по правилам `selector-research.md`.
3. Если TC указывает роль (раздел «Роль») — реализуй загрузку сохранённого состояния сессии через `roleStorageState()` вместо реализации собственного шага аутентификации для стартовой учётной записи. Подробности — в `playwright-implementation.md`, раздел «Роли и подготовленные сессии в реализации».
4. Реализуй сам TC, используя готовые реализации Action. Реализация должна соответствовать только утверждённому TC и используемым Action.

Действуй по:

- `test-data-and-environment.md`;
- `playwright-implementation.md`.

### Проверка актуальности реализации по хэшу

Перед использованием существующей `actions/AA-<CODE>.ts` сравни хэши источника (`source-hash-signature`, `source-hash-logic`), зафиксированные в первой строке файла, с текущим документом Action (`document_authoring.py hash --kind aa --part signature|logic`). При расхождении — это сигнал, что редактирование Action было выполнено в обход `/edit-aa` (несогласованное состояние). Верни `BLOCKED`, не перегенерируй файл молча.

## 6. Проверка

Возьми доступные команды из `package.json` и фактической конфигурации проекта.

Выполни применимые проверки:

- форматирование затронутых файлов;
- lint;
- TypeScript typecheck;
- целевой тест;
- затронутые существующие тесты при изменении общего кода.

Не заявляй о проверке, которую не запускал.

## 7. Критерии завершения

Работа может получить статус `DONE`, если:

- требования однозначны;
- сценарий исследован через MCP;
- реализация соответствует TC и Action либо команда исследования завершена без реализации;
- необходимые проверки выполнены;
- результат теста зафиксирован и классифицирован;
- риски перечислены.

Результат теста `FAILED` не препятствует статусу работы `DONE`, если тест корректен и выявляет дефект приложения.

Итоговый ответ оформи по `completion-report.md` и правилам `diagnostics.md`.
