# Реализация одного Test Case

## Область применения

Инструкция определяет процесс исследования и реализации одного утверждённого TC.

Работай только с TC, указанным в команде. Не анализируй другие сценарии без необходимости поиска затронутого общего кода.

`test-dependencies.json` при исследовании, реализации и изолированном запуске одного TC не учитывается.

## 1. Загрузка контекста

Прочитай:

1. целевой `TC-*.md`;
2. только AA из его раздела `Зависимости`;
3. спецификации селекторов целевого TC и используемых AA, если они существуют;
4. существующий целевой тест и непосредственно связанный общий код, если они существуют.

Не загружай остальные TC, AA и селекторы заранее.

## 2. Статическая проверка

До работы с интерфейсом проверь:

- существуют ли все указанные AA;
- не противоречат ли TC и AA;
- определено ли одно проверяемое бизнес-условие;
- определены ли обязательные входные данные;
- можно ли получить и создать необходимые данные через UI;
- можно ли однозначно подтвердить один из вариантов успешного результата каждого подготовительного AA;
- совместимы ли последовательные AA;
- не требует ли сценарий существующей бизнес-сущности или результата другого теста.

При блокирующей неоднозначности действуй по корневому `AGENTS.md` и шаблону `blocked-report.md`.

## 3. Dry-run

До запуска MCP сформируй внутренний пошаговый план:

- выбор учётной записи;
- подготовка и генерация данных;
- последовательность AA;
- переходы между страницами;
- значения, передаваемые через контекст теста;
- основная проверка TC.

Отдельное подтверждение dry-run не требуется, если документация однозначна.

## 4. Исследование и проверка выполнимости

Действуй по `selector-research.md`.

До написания тестового кода выполни сценарий через Playwright MCP и проверь:

- выполнимость каждого подготовительного действия;
- передачу данных между шагами;
- достижимость основной проверки;
- достижение одного из вариантов успешного результата каждого AA;
- соответствие наблюдаемого результата основной проверке TC.

При необходимости изменения утверждённой документации верни `BLOCKED`. Документы не изменяй.

## Использование Atomic Action

При выполнении AA достаточно подтвердить один из вариантов, перечисленных в разделе `Варианты успешного результата`. Все перечисленные варианты считаются успешными.

Если ни один вариант не достигнут:

1. считать AA выполненным неуспешно;
2. немедленно остановить выполнение текущего TC;
3. не продолжать основную проверку и последующие действия;
4. классифицировать причину по `diagnostics.md`.

Не добавляй в реализацию ветвление по отрицательным исходам, если оно не требуется отдельным TC. Не превращай неописанный исход в новый результат AA.

Если дальнейшим шагам нужен конкретный успешный вариант, используй только выходные данные, явно определённые в AA.

## 5. Реализация

Если команда разрешает изменение кода, действуй по:

- `test-data-and-environment.md`;
- `playwright-implementation.md`.

Реализация должна соответствовать только утверждённому TC и используемым AA.

## 6. Проверка

Возьми доступные команды из `package.json` и фактической конфигурации проекта.

Выполни применимые проверки:

- форматирование затронутых файлов;
- lint;
- TypeScript typecheck;
- целевой тест;
- затронутые существующие тесты при изменении общего кода.

Не заявляй о проверке, которую не запускал.

## 7. Критерии завершения

Работа может получить статус `DONE`, если:

- требования однозначны;
- сценарий исследован через MCP;
- реализация соответствует TC и AA либо команда исследования завершена без реализации;
- необходимые проверки выполнены;
- результат теста зафиксирован и классифицирован;
- риски перечислены.

Результат теста `FAILED` не препятствует статусу работы `DONE`, если тест корректен и выявляет дефект приложения.

Итоговый ответ оформи по `completion-report.md` и правилам `diagnostics.md`.
