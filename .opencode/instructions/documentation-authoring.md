# Создание и редактирование проектной документации

## Область применения

Инструкция применяется командами `/create-aa`, `/create-tc`, `/edit-aa`, `/edit-tc`.

`/create-aa` и `/create-tc` разрешают создать один новый документ. `/edit-aa` и `/edit-tc` разрешают изменить один существующий утверждённый документ — правила см. в разделе «Редактирование существующего документа».

Вне рамок этих команд и правил документация не изменяется, не перезаписывается, не перемещается и не удаляется.

После сохранения новый или изменённый документ считается утверждённым.

## Интерактивный режим

Собирай требования в диалоге.

- Задавай вопросы группами по 3–5 за сообщение. 5 — жёсткий потолок: остальные вопросы переносятся на следующий цикл диалога. Если готово меньше 3 вопросов, не жди — задай их сразу.
- Не повторяй вопросы, на которые пользователь уже ответил.
- Учитывай начальное описание из аргументов команды и сведения текущего диалога.
- Задавай только вопросы, необходимые для однозначного заполнения документа.
- Не придумывай требования, параметры, шаги, результаты и зависимости.
- Не выбирай наиболее вероятную трактовку.
- При полезности предложи конкретную формулировку, но запроси решение пользователя.
- Не переходи к согласованию, пока обязательные сведения не определены.

## Проверка существующих документов

До выбора идентификатора (`/create-aa`, `/create-tc`):

1. Получи список существующих документов соответствующего типа (`document_authoring.py inventory`).
2. Проверь уникальность идентификатора и целевого пути.
3. Проверь отсутствие существующего документа с тем же смыслом.
4. Открывай только документы, необходимые для этой проверки.

При создании TC открой полные документы только тех Action, которые пользователь указал как зависимости.

## Формирование Action

В разделе `Варианты успешного результата` перечисляй только наблюдаемые положительные состояния, каждое из которых подтверждает успешное выполнение Action.

- Не описывай отрицательные результаты, ошибки, таймауты и состояние «другое».
- Каждый перечисленный вариант является достаточным условием успешности действия.
- Любой исход, не совпавший ни с одним перечисленным вариантом, считается неуспешным выполнением Action.
- Если вызывающему TC необходимо знать, какой именно успешный вариант достигнут, явно опиши это значение в разделе `Выходные данные`.
- Если допустим только один успешный результат, укажи один элемент списка.
- Не указывай формат, тип данных или технические ограничения параметра в разделе `Входные параметры` — Action всегда получает готовое конкретное значение через TC (см. «Формирование Test Case» ниже).
- Если у Action нет наблюдаемого интерфейса (чисто вычислительный генератор данных или иное получение значения без UI) — раздел `Варианты успешного результата` всё равно обязателен, даже если условие формальное, например: «Значение сгенерировано и соответствует формату.».

## Формирование Test Case

### Роль

Спроси пользователя, начинается ли TC с уже подготовленной сессии, или выполняет собственную аутентификацию как часть сценария.

Если используется роль — покажи список существующих ролей из `docs/roles.md` (код и название) для выбора, не проси вводить код свободным текстом. Если реестр ролей пуст или нужной роли нет — сообщи об этом явно и предложи два варианта: продолжить без роли (собственная аутентификация в сценарии) или прерваться и сначала выполнить `/configure-roles`.

Если роль не используется — раздел «Роль» содержит строго «Роль не используется.».

Если роль используется — соответствующая начальная учётная запись не описывается повторно как группа тестовых данных, и в «Описании сценария» не появляется шаг аутентификации для неё. Это не исключает более поздних самостоятельных шагов аутентификации в сценарии для сущностей, создаваемых самим тестом (см. динамическую группу ниже) — роль покрывает только стартовое состояние.

### Тестовые данные

Организуй данные именованными группами (`###`-подразделы). Определи тип каждой группы:

- **статическая** — значения известны заранее, перечисляются в группе;
- **динамическая** — значения формируются по ходу сценария; вместо значений укажи Action, при выполнении которого группа формируется (без номера шага — TC может редактироваться вручную, нумерация шагов нестабильна). Источником динамической группы может быть как обычный UI-Action (создание сущности через интерфейс), так и Action-генератор данных (см. ниже) — оформление группы в TC одинаковое в обоих случаях.

Формат параметра в TC не указывается ни в одном из двух типов группы. Явное намерение оставить поле пустым фиксируется прямо в статической группе: `**Поле** — пусто.`

Если название поля в группе совпадает с названием заполняемого или проверяемого поля формы/параметра Action — в шаге сценария ссылайся на группу одной фразой, не расписывай поля по отдельности.

### Данные из внешнего источника и генераторы

Реализация TC не должна вызывать генераторы данных (Faker и аналоги) напрямую в коде теста. Такая генерация — как и получение любых данных из внешнего источника (например, кода подтверждения через тестовую форму) — оформляется как обычный Action, с собственным документом и реализацией (см. «Формирование Action» выше, включая правило про формальный успешный результат для Action без UI). TC ссылается на такой Action как на источник динамической группы тестовых данных — без особого синтаксиса, без пометок «генерируется».

Формат/ограничения значения, которое производит такой Action, описываются в его собственном разделе `Выходные данные` — это то же самое поле, что и у любого другого Action, ничего нового.

### Зависимости

Для каждой зависимости придумай короткое мнемоническое название, дословно совпадающее с тем, как Action будет называться в шагах «Описания сценария» этого TC. Не копируй сюда назначение Action из его собственного документа — это локальное для TC короткое имя, не описание.

### Описание сценария

Каждый шаг, вызывающий Action, оформляй как:

`Выполнить <Мнемоническое название> (`<AA-ID>`), используя <ссылка на группу тестовых данных>.`

Код Action указывай при каждом вызове, включая повторные вызовы одной и той же Action в одном сценарии — трассируемость шага не должна зависеть от того, что было выше по тексту.

Не расписывай в шаге отдельные значения параметров или названия полей, совпадающие с уже названной группой тестовых данных.

## Подготовка проекта

После завершения опроса:

1. Проверь полноту и внутреннюю согласованность документа.
2. Определи идентификатор и целевой путь.
3. Покажи целевой путь.
4. Покажи полный текст документа.
5. Запроси явное подтверждение сохранения именно этой редакции.

До подтверждения не создавай и не изменяй файл.

## Согласование

Пользователь может подтвердить редакцию, потребовать изменения, дополнить требования или отменить создание/изменение.

После любого изменения снова покажи полный текст документа и запроси подтверждение.

Подтверждение предыдущей редакции не распространяется на изменённую редакцию.

## Сохранение (создание)

Непосредственно перед записью повторно проверь:

- уникальность идентификатора;
- отсутствие файла по целевому пути;
- наличие обязательных разделов;
- соответствие идентификатора заголовку, разделу `Код` и имени файла;
- существование всех указанных ссылок на другие документы.

Используй `document_authoring.py validate --mode create`, затем, при успехе, `create`.

Создай только один согласованный файл.

Не создавай автоматически:

- JSON-спецификацию селекторов (создаётся только на `/implement-tc`, см. `selector-research.md`);
- тестовый код;
- другой TC или Action;
- сопутствующие файлы.

Если целевой файл появился во время согласования, не перезаписывай его. Верни `BLOCKED` и предложи новый идентификатор.

## Редактирование существующего документа (`/edit-aa`, `/edit-tc`)

1. Загрузи текущую утверждённую редакцию, покажи пользователю.
2. Веди диалог изменений по правилам «Интерактивного режима» (тот же батчинг вопросов).
3. После согласования новой редакции определи, что изменилось:
   - для Action — вычисли `document_authoring.py hash --kind aa --part signature` и `--part logic` по новой редакции; сравни со значениями хэшей, зафиксированными в комментарии существующего `actions/AA-<CODE>.ts` (если файла нет — реализации ещё не было, менять нечего);
   - для TC — вычисли `hash --kind tc`; сравни со значением в комментарии существующего `.spec.ts` (если файла нет — менять нечего).
4. Последствия для программной реализации (что именно удаляется, каскад на зависимые TC при смене сигнатуры Action) описаны в `playwright-implementation.md`, раздел «Редактирование Action и TC» — следуй ему, не дублируй логику здесь.
5. Сохрани документ через `document_authoring.py validate --mode update`, затем, при успехе, `update` (не `create` — целевой файл уже существует).
6. Не создавай при этом новых TC/Action и не изменяй документы, не являющиеся целью редактирования.

## Завершение

После сохранения (создания или изменения) сообщи:

- идентификатор документа;
- путь файла;
- что документ сохранён и теперь считается утверждённым;
- для `/edit-aa` со сменой сигнатуры — список затронутых TC, чьи реализации были удалены и потребуют повторного `/implement-tc`.

Если пользователь отменил создание или изменение, не изменяй файлы проекта.
