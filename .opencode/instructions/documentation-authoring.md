# Создание и редактирование проектной документации

## Область применения

Инструкция применяется командами `/create-aa`, `/create-tc`, `/edit-aa`, `/edit-tc`.

`/create-aa` и `/create-tc` разрешают создать один новый документ. `/edit-aa` и `/edit-tc` разрешают изменить один существующий утверждённый документ — правила см. в разделе «Редактирование существующего документа».

Вне рамок этих команд и правил документация не изменяется, не перезаписывается, не перемещается и не удаляется.

После сохранения новый или изменённый документ считается утверждённым.

## Интерактивный режим

Собирай требования в диалоге.

- Задавай вопросы группами по 3–5 за сообщение. 5 — жёсткий потолок: остальные вопросы переносятся на следующий цикл диалога. Если готово меньше 3 вопросов, не жди — задай их сразу.
- Не повторяй вопросы, на которые пользователь уже ответил.
- Учитывай начальное описание из аргументов команды и сведения текущего диалога.
- Задавай только вопросы, необходимые для однозначного заполнения документа.
- Не придумывай требования, параметры, шаги, результаты и зависимости.
- Не выбирай наиболее вероятную трактовку.
- При полезности предложи конкретную формулировку, но запроси решение пользователя.
- Не переходи к согласованию, пока обязательные сведения не определены.

## Проверка существующих документов

До выбора идентификатора (`/create-aa`, `/create-tc`):

1. Получи список существующих документов соответствующего типа (`document_authoring.py inventory`).
2. Проверь уникальность идентификатора и целевого пути.
3. Проверь отсутствие существующего документа с тем же смыслом.
4. Открывай только документы, необходимые для этой проверки.

При создании TC открой полные документы только тех AA, которые пользователь указал как зависимости.

## Формирование Atomic Action

В разделе `Варианты успешного результата` перечисляй только наблюдаемые положительные состояния, каждое из которых подтверждает успешное выполнение AA.

- Не описывай отрицательные результаты, ошибки, таймауты и состояние «другое».
- Каждый перечисленный вариант является достаточным условием успешности действия.
- Любой исход, не совпавший ни с одним перечисленным вариантом, считается неуспешным выполнением AA.
- Если вызывающему TC необходимо знать, какой именно успешный вариант достигнут, явно опиши это значение в разделе `Выходные данные`.
- Если допустим только один успешный результат, укажи один элемент списка.
- Не указывай формат, тип данных или технические ограничения параметра в разделе `Входные параметры` — AA всегда получает готовое конкретное значение через TC (см. «Формирование Test Case» ниже).

## Формирование Test Case

### Тестовые данные

Организуй данные именованными группами (`###`-подразделы). Определи тип каждой группы:

- **статическая** — значения известны заранее, перечисляются в группе;
- **динамическая** — значения формируются по ходу сценария; вместо значений укажи AA, при выполнении которого группа формируется (без номера шага — TC может редактироваться вручную, нумерация шагов нестабильна);
- **генерируемая** — вместо значений укажи требования к формату и правилам генерации для каждого поля. Способ генерации (например, Faker) не документируется, выбирается свободно на этапе `/implement-tc`.

Формат параметра указывай только в генерируемой группе. В статической и динамической группах формат не указывается. Явное намерение оставить поле пустым фиксируется прямо в статической группе: `**Поле** — пусто.`

Если название поля в группе совпадает с названием заполняемого или проверяемого поля формы/параметра AA — в шаге сценария ссылайся на группу одной фразой, не расписывай поля по отдельности.

### Зависимости

Для каждой зависимости придумай короткое мнемоническое название, дословно совпадающее с тем, как AA будет называться в шагах «Описания сценария» этого TC. Не копируй сюда назначение AA из его собственного документа — это локальное для TC короткое имя, не описание.

### Описание сценария

Каждый шаг, вызывающий AA, оформляй как:

`Выполнить <Мнемоническое название> (`<AA-ID>`), используя <ссылка на группу тестовых данных>.`

Код AA указывай при каждом вызове, включая повторные вызовы одной и той же AA в одном сценарии — трассируемость шага не должна зависеть от того, что было выше по тексту.

Не расписывай в шаге отдельные значения параметров или названия полей, совпадающие с уже названной группой тестовых данных.

## Подготовка проекта

После завершения опроса:

1. Проверь полноту и внутреннюю согласованность документа.
2. Определи идентификатор и целевой путь.
3. Покажи целевой путь.
4. Покажи полный текст документа.
5. Запроси явное подтверждение сохранения именно этой редакции.

До подтверждения не создавай и не изменяй файл.

## Согласование

Пользователь может подтвердить редакцию, потребовать изменения, дополнить требования или отменить создание/изменение.

После любого изменения снова покажи полный текст документа и запроси подтверждение.

Подтверждение предыдущей редакции не распространяется на изменённую редакцию.

## Сохранение (создание)

Непосредственно перед записью повторно проверь:

- уникальность идентификатора;
- отсутствие файла по целевому пути;
- наличие обязательных разделов;
- соответствие идентификатора заголовку, разделу `Код` и имени файла;
- существование всех указанных ссылок на другие документы.

Используй `document_authoring.py validate --mode create`, затем, при успехе, `create`.

Создай только один согласованный файл.

Не создавай автоматически:

- JSON-спецификацию селекторов (создаётся только на `/implement-tc`, см. `selector-research.md`);
- тестовый код;
- другой TC или AA;
- сопутствующие файлы.

Если целевой файл появился во время согласования, не перезаписывай его. Верни `BLOCKED` и предложи новый идентификатор.

## Редактирование существующего документа (`/edit-aa`, `/edit-tc`)

1. Загрузи текущую утверждённую редакцию, покажи пользователю.
2. Веди диалог изменений по правилам «Интерактивного режима» (тот же батчинг вопросов).
3. После согласования новой редакции определи, что изменилось:
   - для AA — вычисли `document_authoring.py hash --kind aa --part signature` и `--part logic` по новой редакции; сравни со значениями хэшей, зафиксированными в комментарии существующего `actions/AA-<CODE>.ts` (если файла нет — реализации ещё не было, менять нечего);
   - для TC — вычисли `hash --kind tc`; сравни со значением в комментарии существующего `.spec.ts` (если файла нет — менять нечего).
4. Последствия для программной реализации (что именно удаляется, каскад на зависимые TC при смене сигнатуры AA) описаны в `playwright-implementation.md`, раздел «Редактирование AA и TC» — следуй ему, не дублируй логику здесь.
5. Сохрани документ через `document_authoring.py validate --mode update`, затем, при успехе, `update` (не `create` — целевой файл уже существует).
6. Не создавай при этом новых TC/AA и не изменяй документы, не являющиеся целью редактирования.

## Завершение

После сохранения (создания или изменения) сообщи:

- идентификатор документа;
- путь файла;
- что документ сохранён и теперь считается утверждённым;
- для `/edit-aa` со сменой сигнатуры — список затронутых TC, чьи реализации были удалены и потребуют повторного `/implement-tc`.

Если пользователь отменил создание или изменение, не изменяй файлы проекта.
