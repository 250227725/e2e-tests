# Исследование раздела и подготовка материала для AA/TC

## Область применения

Инструкция применяется только командой `/explore`. Разрешает исследовать интерфейс через подключённый MCP-сервис браузерной автоматизации и сохранить черновой материал для последующей формализации через `/create-aa`/`/create-tc`.

Файл исследования — **не утверждённая документация**, не валидируется строго и не требует согласования текста с пользователем перед записью (в отличие от TC/AA). Формализация в реальные AA/TC происходит отдельно, позже, через обычный процесс `documentation-authoring.md` — черновик из файла исследования используется только как исходное описание ($ARGUMENTS), не копируется автоматически.

Команда не создаёт селектор-спецификации — это происходит только на `/implement-tc` (см. `selector-research.md`). В файле исследования могут упоминаться замеченные элементы интерфейса в свободной, описательной форме, без формального формата локаторов.

## Точка входа

Аргумент команды — свободное текстовое описание задачи исследования: откуда начать (URL, учётная запись, навигация до нужного раздела) и что нужно выяснить. Учётная запись указывается пользователем как есть, свободным текстом — не связана с реестром ролей `docs/roles.md`.

Пройди указанный путь через MCP буквально: аутентификация, переходы, клики — как это сделал бы человек, а не предположения о том, что там может быть.

## Исследование

Действуй по тем же принципам, что и `selector-research.md`: не придумывай DOM, роли, тексты и переходы — только то, что реально наблюдается. Изучи процесс полностью в границах, заданных запросом: доступные действия, поля форм, переходы между состояниями, сообщения об ошибках и успехе, ветвления.

Если процесс явно распадается на несколько вариантов одного действия (как в примере с разными типами документов) — исследуй и зафиксируй каждый вариант отдельно.

## Формирование материала

Сохрани результат в `docs/exploration/<тема>.md` (slug из темы исследования, латиницей, через дефис). Если файл с таким именем уже существует — спроси пользователя, обновить его или создать новый с уточняющим именем.

Формат:

```markdown
# Исследование: <Тема>

## Метаданные

- Дата: <YYYY-MM-DD>
- Точка входа: <URL/раздел, учётная запись>
- Задача исследования: <кратко, что просили выяснить>

## Наблюдения

<Свободное описание процесса — переходы, состояния, поля, кнопки, ветвления. Черновой текст, не требует строгого оформления.>

## Кандидаты AA

### <Рабочее название кандидата>

- Возможные входные параметры: <черновой список>
- Наблюдаемые шаги: <черновой список>
- Возможные варианты успешного результата: <черновой список>

<Один раздел на каждый предложенный AA. Если один процесс распадается на несколько вариантов действия — отдельный кандидат на каждый вариант.>

## Кандидаты TC

### <Рабочее название кандидата>

- Возможное проверяемое условие: <черновая формулировка>
- Возможные зависимости (AA): <ссылки на кандидатов выше, по названию>

<Раздел появляется только если в процессе исследования видно завершённое бизнес-условие, а не только переиспользуемое действие. Если такого нет — раздел с пометкой «Кандидаты TC не выявлены.».>

## Открытые вопросы

<Неоднозначности, замеченные во время исследования, которые нужно решить при формализации через `/create-aa`/`/create-tc`. Если вопросов нет — «Открытые вопросы отсутствуют.».>
```

Не переходи к формализации (`/create-aa`/`/create-tc`) в рамках той же команды — `/explore` только готовит материал. Формализация каждого кандидата — отдельный, самостоятельный вызов `/create-aa` или `/create-tc` с текстом соответствующего раздела как начальным описанием, по явному запросу пользователя.

## Завершение

После сохранения сообщи путь к файлу и кратко перечисли, сколько кандидатов AA и TC предложено.
