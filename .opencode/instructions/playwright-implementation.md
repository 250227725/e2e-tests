# Реализация тестов на Playwright

## Архитектура

Рекомендуемое распределение ответственности:

- `tests/` — оркестрация TC и основная проверка;
- `pages/` — страницы и навигация;
- `components/` — повторно используемые части интерфейса;
- `actions/` — программная реализация Action, один файл `AA-<CODE>.ts` на Action;
- `fixtures/` — контекст, тестовые зависимости и резолвер локаторов (см. «Локаторы»);
- `data/` — генерация тестовых данных.

Адаптируйся к фактической структуре проекта. Не перестраивай её без практической необходимости.

## Общий код

- Перед изменением общего кода найди все места его использования.
- Общий метод должен иметь узкую ответственность.
- Изменение не должно молча менять прежнее поведение.
- Для нового поведения предпочитай новый явно названный метод.
- После изменения общего кода запусти затронутые тесты.
- Не создавай крупную абстракцию ради одного сценария.
- Временное дублирование допустимо, пока повторное использование не подтверждено несколькими сценариями.

## Реализация Action

Каждая используемая Action получает обязательную отдельную реализацию — один файл `actions/AA-<CODE>.ts` на Action. Создаётся внутри `/implement-tc`, при первом использовании этой Action (не в `/create-aa` — там ещё нет ни селекторов, ни доступа к реализации).

Функция реализует контракт Action: параметры — как во «Входных параметрах» документа, с учётом контракта передачи параметров из TC (явное значение / явное «пусто» в тестовых данных / отсутствие → дефолт Action).

Различия в использовании одной Action разными TC выражаются **только через параметры вызова**, не через форки или варианты реализации. Если для одного TC нужен вариант поведения, которого Action не предусматривает — это повод для `/edit-aa`, а не для локального обхода в TC.

## Хэш источника в сгенерированных файлах

Первая строка каждого сгенерированного файла содержит хэш источника — используется `/edit-aa`/`/edit-tc` и статической проверкой `test-development.md` для обнаружения рассинхрона с документом.

Для Action (`actions/AA-<CODE>.ts`):

```ts
// source-hash-signature: <hash> source-hash-logic: <hash> (AA-<CODE>.md)
```

Для TC (файл теста):

```ts
// source-hash: <hash> (TC-<CODE>-<NNN>.md)
```

Значения вычисляются через `document_authoring.py hash --kind aa --part signature|logic` и `hash --kind tc` соответственно. Состав хэшируемых разделов зафиксирован в самом скрипте (`AA_HASH_SECTIONS`, `TC_HASH_SECTIONS`) — не дублируй логику вручную.

## Роли и подготовленные сессии в реализации

Если TC указывает роль в разделе «Роль» (не «Роль не используется.»), его файл теста не выполняет собственную аутентификацию для стартовой учётной записи. Вместо этого он загружает сохранённое состояние сессии через резолвер `fixtures/roles.ts` (поддерживается `/configure-roles`, см. `role-configuration.md`):

```ts
import { roleStorageState } from '../fixtures/roles';

test.use({ storageState: roleStorageState('ADMIN') });
```

Не пиши путь к файлу состояния напрямую в TC-файле — только через `roleStorageState()`. Размести вызов `test.use` в начале файла теста (или блока `test.describe`, если в одном файле сочетаются TC с разными ролями). Не вызывай реализацию аутентификации (`actions/AA-AUTH.ts` или аналогичную) для стартовой роли — состояние уже загружено; собственные шаги аутентификации в сценарии (для сущностей, создаваемых самим тестом) реализуются как обычно.

Автоматический запуск `setup`-проекта перед зависимыми тестами обеспечивается `dependencies: ['setup']` в `playwright.config.ts` (настраивается `/configure-roles`) — это работает и при изолированном запуске одного TC через `/run-tc`, отдельной защиты не требуется, в отличие от компромисса с `actions/AA-<CODE>.ts` (см. «Редактирование Action и TC» ниже).

## Локаторы

Локаторы в коде теста не пишутся напрямую. Используется функция-резолвер, читающая соответствующий `*.selectors.json` (см. `selector-research.md`) по семантическому ключу элемента и странице.

Резолвер поддерживает стратегии `role`, `label`, `text`, `testid`, `css` — по значению `locator.primary.strategy`. При недоступности или неудаче основного локатора используется `locator.fallback`, если он не `null`. Если у элемента задано `within` — локатор ищется в пределах родительского элемента той же страницы.

Тестовые файлы и файлы `actions/` не должны содержать длинные CSS-цепочки или locator-строки напрямую — только обращения к резолверу.

## Проверки

### Защитные проверки

Подтверждают успешность подготовительного действия и располагаются рядом с ним.

Защитная проверка Action должна подтвердить достижение хотя бы одного варианта из раздела `Варианты успешного результата`. Все перечисленные варианты считаются положительными и равноправно подтверждают успешность действия.

Она может проверять:

- нужную страницу;
- успешную аутентификацию;
- сохранение формы;
- появление сообщения;
- отображение созданной записи;
- другое положительное постусловие Action.

Если ни один вариант успешного результата не достигнут, проверка должна завершиться ошибкой и остановить текущий TC. Не описывай и не обрабатывай внутри Action отдельные отрицательные результаты, если это не является самостоятельным требованием TC.

### Основная проверка

Подтверждает бизнес-условие TC.

Она должна быть явно отделена, например через `test.step`, и однозначно соответствовать разделу `Условие проверки` TC.

Защитная проверка не заменяет основную.

## Ожидания и асинхронность

Используй auto-waiting Playwright и ожидание наблюдаемого состояния интерфейса:

- URL;
- видимость или скрытие элемента;
- доступность элемента;
- текст;
- состояние формы;
- завершившийся переход, наблюдаемый через UI.

Без доказанной необходимости запрещены:

- `page.waitForTimeout`;
- произвольные задержки;
- `force: true`;
- подавление исключений;
- бесконечные или чрезмерные повторы;
- retries для маскировки нестабильности;
- увеличение timeout вместо диагностики.

Специальный порог времени из TC или Action является бизнес-требованием. Технический timeout Playwright не должен изменять его смысл.

## Диагностические артефакты

Предпочтительная базовая конфигурация:

```ts
use: {
  screenshot: 'only-on-failure',
  trace: 'retain-on-failure',
  video: 'off',
},
reporter: [['html', { open: 'never' }]],
```

Не меняй существующую конфигурацию без необходимости.

Trace, screenshot и HTML-отчёт могут содержать чувствительные данные. Не публикуй и не прикладывай их без проверки содержимого.

## Редактирование Action и TC

Правила интерактивного диалога и сохранения документа — в `documentation-authoring.md`. Здесь — последствия для программной реализации.

### `/edit-aa`

После согласования новой редакции Action сравни хэши источника новой редакции (`document_authoring.py hash --kind aa --part signature|logic`) с хэшами, зафиксированными в существующем `actions/AA-<CODE>.ts` (если файла нет — реализации не было, менять нечего):

- **Изменилась сигнатура** (`source-hash-signature` не совпадает — затронуты «Входные параметры» или «Выходные данные»): найди все зависимые TC через `document_authoring.py dependents --kind aa --id AA-<CODE>`. Удали `actions/AA-<CODE>.ts`, `AA-<CODE>.selectors.json`, а также, для каждого найденного TC, его файл теста и `TC-<...>.selectors.json`. Перечисли все затронутые TC в итоговом отчёте как требующие повторного `/implement-tc`.
- **Изменилась только логика** (`source-hash-logic` не совпадает, сигнатура та же): удали только `actions/AA-<CODE>.ts` и `AA-<CODE>.selectors.json`. Зависимые TC не трогай.
- **Изменилось только «Назначение»**: ничего не удаляй.

Удалённые файлы пересоздаются естественным образом — следующий `/implement-tc` по любому зависящему TC создаст их заново, как при первом использовании Action.

### `/edit-tc`

После согласования новой редакции сравни хэш (`hash --kind tc`) с хэшем в существующем файле теста (если файла нет — менять нечего). При любом расхождении — удали файл теста целиком и `TC-<...>.selectors.json`. Частичного обновления нет: реализация TC пересоздаётся полностью следующим `/implement-tc`.

### Известное ограничение (принятый компромисс)

Если TC, зависимость которого была удалена по `/edit-aa`, запущен через `/run-tc` в обход предварительного `/implement-tc` — тест упадёт с ошибкой импорта модуля из `actions/`. Это ожидаемое поведение, не требующее отдельной защиты — диагностика этого случая описана в `diagnostics.md`.
