# Реализация тестов на Playwright

## Архитектура

Рекомендуемое распределение ответственности:

- `tests/` — оркестрация TC и основная проверка;
- `pages/` — страницы и навигация;
- `components/` — повторно используемые части интерфейса;
- `actions/` — составные UI-действия;
- `fixtures/` — контекст и тестовые зависимости;
- `data/` — генерация тестовых данных.

Адаптируйся к фактической структуре проекта. Не перестраивай её без практической необходимости.

## Общий код

- Перед изменением общего кода найди все места его использования.
- Общий метод должен иметь узкую ответственность.
- Изменение не должно молча менять прежнее поведение.
- Для нового поведения предпочитай новый явно названный метод.
- После изменения общего кода запусти затронутые тесты.
- Не создавай крупную абстракцию ради одного сценария.
- Временное дублирование допустимо, пока повторное использование не подтверждено несколькими сценариями.

AA является документационной абстракцией. Не создавай отдельный класс или функцию для каждого AA без необходимости повторного использования.

## Локаторы

Используй локаторы, исследованные по `selector-research.md`.

Тестовые файлы не должны содержать длинные CSS-цепочки. Локаторы должны находиться рядом с соответствующей страницей или компонентом, если такая инкапсуляция оправдана структурой проекта.

## Проверки

### Защитные проверки

Подтверждают успешность подготовительного действия и располагаются рядом с ним.

Защитная проверка AA должна подтвердить достижение хотя бы одного варианта из раздела `Варианты успешного результата`. Все перечисленные варианты считаются положительными и равноправно подтверждают успешность действия.

Она может проверять:

- нужную страницу;
- успешную аутентификацию;
- сохранение формы;
- появление сообщения;
- отображение созданной записи;
- другое положительное постусловие AA.

Если ни один вариант успешного результата не достигнут, проверка должна завершиться ошибкой и остановить текущий TC. Не описывай и не обрабатывай внутри AA отдельные отрицательные результаты, если это не является самостоятельным требованием TC.

### Основная проверка

Подтверждает бизнес-условие TC.

Она должна быть явно отделена, например через `test.step`, и однозначно соответствовать разделу `Условие проверки` TC.

Защитная проверка не заменяет основную.

## Ожидания и асинхронность

Используй auto-waiting Playwright и ожидание наблюдаемого состояния интерфейса:

- URL;
- видимость или скрытие элемента;
- доступность элемента;
- текст;
- состояние формы;
- завершившийся переход, наблюдаемый через UI.

Без доказанной необходимости запрещены:

- `page.waitForTimeout`;
- произвольные задержки;
- `force: true`;
- подавление исключений;
- бесконечные или чрезмерные повторы;
- retries для маскировки нестабильности;
- увеличение timeout вместо диагностики.

Специальный порог времени из TC или AA является бизнес-требованием. Технический timeout Playwright не должен изменять его смысл.

## Диагностические артефакты

Предпочтительная базовая конфигурация:

```ts
use: {
  screenshot: 'only-on-failure',
  trace: 'retain-on-failure',
  video: 'off',
},
reporter: [['html', { open: 'never' }]],
```

Не меняй существующую конфигурацию без необходимости.

Trace, screenshot и HTML-отчёт могут содержать чувствительные данные. Не публикуй и не прикладывай их без проверки содержимого.
