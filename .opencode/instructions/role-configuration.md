# Роли и подготовленные сессии

## Область применения

Инструкция описывает лёгкий реестр ролей (`docs/roles.md`) и процесс команды `/configure-roles`. В отличие от TC/Action, реестр ролей **не является утверждённой документацией** и не валидируется строго через `document_authoring.py validate` — только проверкой существования упомянутых Action (`check-roles`).

## Формат `docs/roles.md`

Каждая роль — своя, полностью независимая подготовка с одной точкой захвата состояния в конце (роли не делят между собой физическую цепочку подготовки, даже если их шаги текстуально совпадают):

```markdown
## <Название роли> (`<ROLE-CODE>`)

- Файл состояния: `<произвольный путь, например playwright/.auth/admin.json>`
- Подготовка: `AA-<CODE>` (комментарий) → `AA-<CODE>` (комментарий) → `AA-<CODE>` (комментарий)
```

«Файл состояния» — явное поле, значение которого не вычисляется из `<ROLE-CODE>` по формуле (никакого правила регистра, замены дефисов и т.п.). Путь выбирает автор роли при первом `/configure-roles`, дальше он неизменен, пока роль не изменена повторно.

Состояние захватывается после последнего шага подготовки роли.

## Резолвер (`fixtures/roles.ts`)

`/configure-roles` поддерживает сгенерированный файл-резолвер — единственное место в коде, где код роли превращается в путь к файлу состояния:

```ts
// fixtures/roles.ts — генерируется и поддерживается /configure-roles, не редактировать вручную
const ROLE_STATE_PATHS: Record<string, string> = {
  ADMIN: 'playwright/.auth/admin.json',
};

export function roleStorageState(code: string): string {
  const path = ROLE_STATE_PATHS[code];
  if (!path) {
    throw new Error(`Неизвестная роль: ${code}. Проверьте docs/roles.md и выполните /configure-roles при необходимости.`);
  }
  return path;
}
```

Значения в `ROLE_STATE_PATHS` — прямая копия поля «Файл состояния» из `docs/roles.md` для каждой роли, не пересчитываются. TC-файлы используют только `roleStorageState('<CODE>')`, никогда не пишут путь напрямую — см. `playwright-implementation.md`.

## Процесс `/configure-roles`

1. Показать текущий `docs/roles.md` (или отметить, что реестр пуст).
2. Спросить, что нужно: добавить роль / изменить / удалить. Дальше — диалог по правилам «Интерактивного режима» из `documentation-authoring.md` (тот же батчинг вопросов 3–5).
3. **При удалении или переименовании кода роли** — до подтверждения проверь и покажи пользователю список TC, ссылающихся на неё: `document_authoring.py role-usage --id <ROLE-CODE>`. Если список не пуст, явно предупреди, что эти TC будут ссылаться на несуществующую роль (при следующей проверке документации это будет поймано как `UNKNOWN_ROLE`, при реализации — `BLOCKED`). Удаление не блокируется автоматически — решение остаётся за пользователем, но предупреждение обязательно.
4. Для новой или изменяемой роли — код, название, путь к файлу состояния (произвольный, предложи разумное значение по умолчанию, например `playwright/.auth/<code в нижнем регистре>.json`, но дай пользователю изменить), полная независимая последовательность Action с комментарием к каждому шагу.
5. Проверить существование каждой указанной Action: `document_authoring.py check-roles` (после предварительной записи черновика реестра во временный буфер, или логически эквивалентной проверкой перед сохранением).
6. После подтверждения:
   - обновить `docs/roles.md`;
   - обновить `fixtures/roles.ts` — синхронизировать `ROLE_STATE_PATHS` с реестром (добавить/изменить/удалить запись);
   - обновить или создать setup-файл (например, `tests/roles.setup.ts`) — реализация подготовки через существующие функции `actions/AA-<CODE>.ts`, сохранение состояния по завершении подготовки роли (путь — то же значение, что в `docs/roles.md` и `fixtures/roles.ts`);
   - обновить `playwright.config.ts`: обеспечить существование `setup`-проекта и зависимость `dependencies: ['setup']` у остальных проектов. При первой роли — создать эту структуру целиком. При последующих изменениях — идемпотентно проверить и дополнить, не переписывать разрушительно уже существующую конфигурацию.
7. `playwright/.auth/` (или каталог, фактически выбранный для файлов состояния) — добавить в `.gitignore`, если ещё не добавлено: файлы состояния содержат живые сессионные токены, коммитить нельзя.

## Использование роли в TC

TC ссылается на роль через отдельный раздел `## Роль` (не через группу тестовых данных — см. `documentation-authoring.md`, раздел «Формирование Test Case» → «Роль»):

```markdown
## Роль

`ADMIN` — Администратор.
```

Если роль не используется — раздел содержит строго «Роль не используется.».

`document_authoring.py validate --kind tc` автоматически проверяет существование указанной роли в `docs/roles.md` (код ошибки `UNKNOWN_ROLE`). При создании TC (`/create-tc`) агент показывает список существующих ролей для выбора, не просит вводить код свободным текстом — правило диалога в `documentation-authoring.md`.

TC с указанной ролью не описывает в «Описании сценария» собственный шаг аутентификации для стартовой учётной записи — сценарий начинается уже в аутентифицированном состоянии. Механика загрузки состояния в коде (`roleStorageState()`) — в `playwright-implementation.md`, раздел «Роли и подготовленные сессии в реализации».

## Базовые роли и значения по умолчанию

Большинство ролей ожидаемо покрываются значениями по умолчанию соответствующих Action — отдельная правка `docs/roles.md` для этого не требуется. Если конкретной роли нужны нестандартные значения (например, отдельная тестовая учётная запись) — это явное решение разработчика при настройке роли, `/configure-roles` не подставляет их самостоятельно.

## Согласованность с Action (см. также `/edit-aa`)

`docs/roles.md` не входит в каскад автоматического пересоздания при `/edit-aa` (в отличие от TC) — правки роли делаются вручную через `/configure-roles`, только по решению разработчика. Вместо автоматического действия `/edit-aa` обязан:

- в начале работы — показать, какие роли используют редактируемую Action (`document_authoring.py role-dependents --id <AA-ID>`), наравне с зависимыми TC;
- в конце, если изменилась сигнатура — повторно перечислить эти роли в отчёте как требующие ручной проверки.

Подробности — в `playwright-implementation.md`, раздел «Редактирование Action и TC».

## Устаревание состояния

Setup-проект выполняется заново при каждом запуске `npx playwright test` (через `dependencies` в `playwright.config.ts`), поэтому устаревание сохранённого состояния в рамках одного прогона не является проблемой. Если приложение выдаёт короткоживущие токены — это может потребовать отдельного внимания при диагностике `ENVIRONMENT`-ошибок, не специфично для механизма ролей.
