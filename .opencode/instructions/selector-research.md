# Исследование интерфейса и локаторов

## Область применения

Локаторы определяются только после исследования реального интерфейса через подключённый MCP-сервис браузерной автоматизации.

Не придумывай DOM, атрибуты, роли и локаторы.

Во время интерактивного создания документа (`/create-aa`, `/create-tc`) агент может исследовать реальный интерфейс через MCP, чтобы точнее сформулировать шаги и параметры — но не создаёт при этом никаких файлов, ни кода, ни спецификации селекторов. Такое исследование — вспомогательное, для диалога, не для фиксации результата.

## Исследование

Для каждого используемого элемента:

1. определи его назначение в TC или Action;
2. изучи роль, доступное имя, подпись, видимый текст, атрибуты и локальную структуру DOM;
3. проверь состояния загрузки, переходы и изменение доступности элемента;
4. определи Playwright locator;
5. проверь точность и отсутствие неоднозначного совпадения;
6. оцени надёжность, риск и альтернативу.

Результат исследования на этапе `/research-tc` фиксируется только в отчёте (`completion-report.md`/`blocked-report.md`) — файл спецификации не создаётся. Файл спецификации создаётся только на этапе `/implement-tc` (см. «Selector-спецификации» ниже).

## Приоритет локаторов

Обычно предпочитай:

1. роли и доступные имена (`strategy: role`);
2. связанные подписи полей (`strategy: label`);
3. устойчивый видимый текст (`strategy: text`);
4. локальные тестовые атрибуты (`strategy: testid`);
5. короткие CSS-селекторы как крайний вариант (`strategy: css`).

Порядок не является механическим. `testid` не считается лучшим вариантом автоматически.

Без обоснования не используй XPath, длинные CSS-цепочки, динамические классы, случайный порядок элементов, `nth()` и текст с нестабильными данными.

## Недостаточная разметка

Если устойчивый locator построить нельзя:

1. классифицируй проблему как `MARKUP`;
2. предложи локальное изменение разметки;
3. не изменяй код приложения;
4. явно укажи риск временного хрупкого locator.

## Selector-спецификации

Формат — JSON. Создаётся и обновляется только на этапе `/implement-tc`, для TC и всех задействованных им Action. Файлы хранятся отдельно для каждого документа:

- `docs/atomic-actions/AA-<CODE>.selectors.json`;
- `docs/test-cases/TC-<CODE>-<NNN>.selectors.json`.

Схема (см. также `.opencode/templates/selector-specification.schema.json` и пример `.opencode/templates/selector-specification.example.json`):

```json
{
  "document": "TC-<CODE>-<NNN>",
  "pages": [
    {
      "name": "<Название страницы>",
      "route": "<Маршрут>",
      "elements": {
        "<семантический_ключ_элемента>": {
          "description": "<Человекочитаемое описание назначения, надёжности и риска элемента.>",
          "locator": {
            "primary": { "strategy": "role|label|text|testid|css", "...": "параметры стратегии" },
            "fallback": null
          },
          "within": null
        }
      }
    }
  ]
}
```

- `document` — идентификатор документа, которому принадлежит спецификация.
- `pages` — массив страниц, на которых используются элементы (TC может затрагивать несколько страниц).
- `elements` внутри каждой страницы — семантический ключ элемента (придумывает агент при исследовании, дальше остаётся стабильным) → описание, локатор, ссылка на родительский элемент.
- `locator.primary`/`locator.fallback` — стратегия и её параметры; `fallback` может быть `null`.
- `within` — ключ родительского элемента **на той же странице**, для составных/повторяющихся локаторов (например, кнопка в строке таблицы), либо `null`.

Правила:

- Селектор принадлежит документу, непосредственно использующему элемент.
- TC не дублирует локаторы Action.
- Не включай элементы, не используемые документом.
- Записывается и валидируется через `document_authoring.py write-selectors --kind aa|tc --id <ID> --content-file -`.

### Граница применимости

JSON-спецификация покрывает только **дрейф значения локатора** — когда элемент физически тот же, но изменился его технический идентификатор, атрибут или порядок в DOM. Правка JSON без изменения TC/Action/кода решает только этот случай.

Она **не** покрывает: смену роли/типа элемента, исчезновение элемента, появление нового шага в потоке, изменение количества совпадений. В этих случаях требуется новое исследование и, возможно, `/edit-tc`/`/edit-aa`.

### Статус документа

В отличие от TC/Action, JSON-спецификация селекторов — не утверждённая документация, а регенерируемый артефакт реализации. Она свободно перезаписывается при каждом `/implement-tc`, без diff и без запроса подтверждения у пользователя. Расхождение JSON с фактическим интерфейсом устраняется пересборкой спецификации, не через `BLOCKED`.

Расхождение самого TC/Action (бизнес-сценария) с фактическим интерфейсом — отдельный случай, по-прежнему ведёт к `BLOCKED` по общим правилам `AGENTS.md`.
